问题：斜杠指示器顽固 bug——打开网页时，音符按钮上的静音斜杠不显示，要点好几下才出来。之前用 ::after 伪元素实现斜杠，加了定位也修不好。
解决：彻底换了一种方案。不再用伪元素画斜杠，改用 CSS linear-gradient 直接在按钮背景上画一条 45 度的对角线。这样斜杠是按钮本身背景的一部分，不存在"加载不出来"的问题。静音状态用渐变背景 + 半透明白底，播放状态只用半透明白底。
问题 2 — BGM 默认打开
问题：非首页的 BGM 默认是打开的。每次打开网站明明没有音乐，但跳到其他页面就自动开始播放了。
解决：原因是 bgm.js 里从 localStorage 读取了上次的播放状态，上次测试时存了个 true 进去，之后每次打开都会自动播放。改成硬编码 isBgmPlaying = false，不再从 localStorage 读取播放状态，所有页面默认静音。
问题 3 — OGG 格式没声音
问题：往 bgm/ 文件夹加了一首 OGG 格式的歌，但网站没声音。
解决：bgm.js 的歌单里写的还是之前的 MP3 文件名，和实际的 OGG 文件对不上。更新了播放列表的文件路径和歌名就好了。顺便加了上一首/下一首切换功能，以后加歌只需要往歌单数组里加一条就行。
问题 4 — 音乐按钮升级
问题：非首页的音乐按钮只有简单的播放/暂停功能，想切歌得去改代码，不够直观。
解决：把其他页面的音乐按钮升级成了悬停展开面板。鼠标放上去会自动向左展开，显示当前歌曲名、上一首、播放/暂停、下一首四个控件。不再使用斜杠指示器，改为直接显示播放状态。首页的音乐按钮保持原样，因为它控制的是视频声音，不是 BGM。
问题 9 — 悬停面板点不到
问题：音乐按钮改成悬停展开面板后，鼠标从按钮往面板方向移的时候面板就消失了，根本点不到播放按钮。
解决：放弃悬停展开，改成纯点击控制。点击音符按钮展开面板，再点一次收回。CSS 从 :hover 选择器改成 .open 类名控制，JS 里用 classList.toggle('open') 切换，简单直接。
问题 10 — 播放视觉反馈
问题：BGM 播放时没有视觉反馈，不知道音乐是不是在放。
解决：加了旋转动画——BGM 播放时音符图标会以中心为原点顺时针匀速旋转。CSS 用 @keyframes musicSpin 实现 3 秒一圈的旋转，bgm.js 的 updatePlayButton() 函数里根据播放状态切换 .playing 类名来控制动画的启停。

?? 追番系统 · 基础建设

问题 11 — 追番卡片重构
问题：追番列表的卡片只有 emoji 图标，没有番剧封面，不够直观。而且想添加新番剧得改代码，不方便。
解决：把追番卡片重构成了带 B 站封面的样式，点击卡片直接跳转到 B 站番剧页面。在列表末尾加了一个虚线边框的"+"按钮卡片，点击弹出添加窗口，输入 B 站链接、番剧名称和评分就能添加新卡片。数据用 localStorage 持久化存储，刷新页面不会丢失。卡片悬停时有放大效果。
问题 12 — 关于我页面白屏
问题："关于我"页面白屏，所有内容、樱花特效都加载不出来，音乐按钮也点不动，只有背景图。
解决：两个 JS 错误叠加导致的。一是 showTab() 函数用了 event.target，页面初次加载时 event 未定义；二是 renderAnimeGrid() 里调用了 observer.observe()，但 observer 变量定义在它后面，执行到这里就报 ReferenceError。两个错误任何一个都会让后续脚本全部停摆。修复方式：showTab 改成传 this 参数，observer 定义移到 renderAnimeGrid() 之前。
问题 13 — 追番管理系统升级
问题：追番列表的添加功能太随意——随便填个其他网站的链接也能添加进去，番剧名称要手动输入很麻烦，而且之前默认列表里的封面链接全是假的（用 media ID 拼的 URL 根本不是真实封面地址），导致所有封面都加载失败。另外也没有删除功能，加错了只能清空本地数据重来。
解决：做了一次完整的追番管理系统升级。首先加了 URL 校验，只接受 bilibili.com/bangumi/ 的 md/ep 链接，其他网站直接拒绝。粘贴 B 站链接后会尝试调用 B 站 API 自动获取番剧名称填入（受跨域限制可能失败，失败就手动填）。每张卡片左上角加了隐藏的删除按钮，鼠标悬停才显示，点击弹出带封面和名称的确认弹窗。标题栏右侧新增"批量删除"和"批量添加"两个按钮——批量删除进入选择模式后，卡片上出现红色 ? 覆盖层，选完后二次确认列出所有待删番剧；批量添加给一个文本框，可以一次粘贴多个链接（换行、逗号、空格分隔），自动校验并跳过重复项。同时清理了默认列表里所有假的封面 URL，改成空字符串用渐变色兜底。

?? 追番系统 · CORS 之战

问题 14 — CORS 拦截与批量删除优化
问题：问题 13 做的自动获取名称和封面实际上不工作——B 站 API 有 CORS 限制，从静态网站用 fetch() 调用会被浏览器拦截。另外批量删除的体验不好，进入选择模式后没有确认/取消按钮在旁边，误触了还得删一个才能退出。评分也要改成自动获取，不要手动输入。
解决：把 API 调用方式从 fetch() 换成了 JSONP（动态创建 <script> 标签），绕过了 CORS 限制。现在粘贴 B 站链接后能自动获取番剧名称、封面和评分，封面还会在弹窗里预览。默认列表的封面和评分也会在页面加载后逐个自动补全。批量删除体验优化：进入选择模式后，原来的"批量删除/批量添加"按钮自动替换为"确认删除/取消"按钮，取消就能直接退出，不用额外操作。选择模式下左上角的单个删除按钮自动隐藏，避免误触。手动评分输入框全部移除，评分改为从 B 站 API 自动获取，显示在卡片右上角。
问题 15 — 简化输入与 CORS 代理
问题：添加番剧时要输入完整的 B 站链接太麻烦，而且 JSONP 方式实际上也不工作（B 站 API 不支持 JSONP 回调），自动获取名称、封面、评分一直没生效。
解决：做了两个改进。第一，简化输入格式：不再要求输入完整链接，改成只输入 B 站番剧页面的 md 编号（如 md26367205），系统自动拼接完整 URL。输入框的 placeholder 和提示文字都更新了，批量添加也改成支持多个 md 编号（换行、空格、逗号分隔）。第二，修复自动获取：把 JSONP 方式替换成直接 fetch() + CORS 代理兜底。先尝试直接请求 B 站 API（有些接口支持跨域），如果失败就依次尝试 corsproxy.io 和 allorigins.win 两个公共代理。现在输入 md 编号后能自动获取番剧名称、封面和评分，封面会在弹窗里预览，添加后直接显示在卡片上。
问题 16 — 代理不可靠，改手动
问题：问题 15 的 CORS 代理方案也不可靠——公共代理经常不稳定、被限流、甚至被墙，导致自动获取封面、名称、评分的功能依然无法正常工作。用户反馈已经修改验证三次了都没有解决。
解决：彻底放弃了不可靠的 API 自动获取方案，改用更简单直接的手动方式。添加弹窗新增了一个"封面图片链接"输入框，用户可以在 B 站番剧页面右键封面图 → 选择"复制图像链接" → 粘贴到输入框里，输入后会实时预览封面效果。同时给每个番剧卡片添加了编辑按钮（悬停时显示在删除按钮旁边），点击可以修改已有番剧的名称和封面，不用删除重新添加。批量添加暂时只支持输入 md 编号，添加后可以逐个编辑补充封面。这个方案虽然需要用户多操作一步，但 100% 可靠，不再依赖任何第三方服务。
问题 17 — 尽力而为策略
问题：问题 16 的手动方案用户体验不好——用户认为只需要输入 md 编号，名称、封面、评分就应该全部自动获取，不应该手动填写。而且之前的方案只自动填充了名称和封面，评分没有被自动获取；批量添加的番剧也没有自动获取功能；默认列表的封面和评分也没有自动补全。
解决：经过多次验证，B 站 API 不返回 Access-Control-Allow-Origin 头，浏览器端 fetch 永远被 CORS 拦截（无论本地 file:// 还是 GitHub Pages HTTPS）。尝试了多种方案：
  • 公共 CORS 代理（corsproxy.io、allorigins.win 等）——不稳定，经常被限流或封锁
  • Cloudflare Worker 专属代理——部署成功，但 B 站屏蔽了 Cloudflare 的 IP 段，返回 -412 "request was banned"
  • Vercel Serverless Function——需要额外配置，且 AWS IP 也可能被 B 站屏蔽
最终采用"尽力而为"的自动填充策略：输入 md 编号后，系统会依次尝试直接请求和公共 CORS 代理获取番剧信息。如果成功，自动填充名称、封面和评分，并在输入框下方显示绿色提示"已获取：番剧名称 (评分 X.X)"；如果全部失败，显示红色提示"自动获取失败，请手动填写番剧名称和封面"，用户可以手动输入。同时保留了编辑按钮和批量添加功能。这个方案在代理可用时提供全自动体验，不可用时优雅降级为手动输入，100% 可靠。

??? 追番系统 · 图片与数据

问题 18 — 封面 http 变 https
问题：封面图片无法加载。B 站 API 返回的封面 URL 是 http:// 开头的，而 GitHub Pages 是 HTTPS 页面，浏览器会拦截 HTTP 图片（混合内容安全策略）。而且之前已经保存到 localStorage 的旧数据里，封面 URL 也是 http:// 的，即使修复了获取逻辑，已有的封面依然显示不出来。
解决：做了两层修复。第一层：在 fetchAnimeMeta 函数里，获取到封面 URL 后立刻把 http:// 转为 https://，// 前缀的也补全为 https:。第二层：添加了一个 fixCoverUrls() 迁移函数，页面加载时自动扫描 localStorage 里已有的番剧数据，把所有 http:// 封面 URL 批量替换为 https://，确保历史数据也能正常显示。
问题 19 — 异步竞态条件
问题：清除数据后第一次添加番剧没反应——点了添加按钮，弹窗关闭了但新番剧没出现在列表里，要重新输入 md 再添加一次才行。
解决：这是一个异步竞态问题。页面加载时 enrichDefaultCovers() 会逐个请求默认番剧列表的封面和评分，这是一个异步操作。如果用户在它还没跑完的时候就添加了新番剧，enrichDefaultCovers 完成后会用旧数据覆盖掉用户刚添加的新数据。修复方案：添加了一个 enrichRunning 标志变量，confirmAdd 在写入数据前会等待 enrichDefaultCovers 完成，避免互相覆盖。
问题 20 — 添加按钮卡住
问题：问题 19 的修复引入了新问题——添加按钮点不动了。因为 enrichDefaultCovers 要遍历 20 个默认番剧，每个都要等 CORS 代理超时，总耗时可能超过一分钟，confirmAdd 一直在等待所以按钮没反应。
解决：两个优化。第一：当用户在输入框开始输入时，设置 enrichCancelled 标志为 true，enrichDefaultCovers 的循环检测到这个标志就立刻中断，不再继续请求剩余的番剧。第二：confirmAdd 的等待加了 3 秒超时上限，如果 3 秒内 enrichDefaultCovers 还没跑完，就强制停止它。这样用户输入后最多等 3 秒就能完成添加，不会因为后台任务卡住。
问题 21 — 番剧"消失"bug
问题：问题 20 的 3 秒超时方案引入了新 bug——第一次添加的番剧"消失了"。超时强制停止后，enrichDefaultCovers 的异步函数其实还在后台运行（正在等待某个 fetch 返回），等它终于拿到数据后，会把自己加载的旧列表保存到 localStorage，覆盖掉用户刚添加的新番剧。第二次添加就正常了，因为那时 enrichDefaultCovers 已经跑完了。
解决：在 enrichDefaultCovers 保存数据之前，增加了一个 enrichCancelled 检查。如果用户已经开始操作（enrichCancelled 为 true），即使异步函数还在跑，最后也不会执行 saveAnimeList，避免用旧数据覆盖新数据。这才是问题 19 竞态条件的完整修复。

?? 追番系统 · JSONP 突破

问题 22 — JSONP 绕过 CORS
问题：封面图片始终获取失败。之前尝试了所有方案：直接 fetch（CORS 拦截）、Cloudflare Worker（B 站屏蔽 IP）、公共 CORS 代理（不稳定/被墙），全部失败。核心问题是 B 站 API 不返回 CORS 头，而所有云服务商的 IP 都被 B 站拉黑了。
解决：找到了一个全新思路——JSONP。浏览器对 <script> 标签没有 CORS 限制，而 B 站 API 恰好支持 ?callback= 参数。原理：动态创建一个 <script> 标签，src 指向 B 站 API 并带上回调函数名，B 站返回的 JavaScript 会直接在我们的页面里执行，完美绕过 CORS。新增了 jsonpFetch 工具函数，fetchAnimeMeta 现在优先用 JSONP 请求，8 秒超时后降级到 CORS 代理。如果 JSONP 成功，名称、封面、评分全自动获取；如果失败（比如 B 站未来取消 JSONP 支持），还有代理兜底。
问题 23 — 云数据库方案
问题：JSONP 也失败了。B 站对 /pgc/review/user 接口做了更严格的限制，即使通过 <script> 标签请求也返回错误。至此，所有浏览器端直接调用 B 站 API 的方案全部宣告失败：CORS 拦截、Cloudflare Worker 被 ban、公共代理不稳定、JSONP 被封锁。
解决：采用了"云数据库"方案——既然浏览器无法实时获取数据，那就提前把数据准备好。用 Python 脚本批量从 B 站 API 获取所有默认番剧的封面、评分、名称，生成一个 anime_database.json 文件，托管在 GitHub Pages 上作为静态数据库。页面加载时一次性获取这个 JSON（同一个域名，没有 CORS 问题），然后从本地缓存中查找。优点：1) 一次 fetch 获取所有数据，比逐个请求快得多；2) 完全绕过 CORS，因为 JSON 文件托管在 GitHub Pages；3) 数据可以离线更新——只需重新运行 Python 脚本并推送即可。对于用户新添加的番剧（不在云数据库中），仍会尝试直接调用 B 站 API 作为兜底。

?? 追番系统 · 稳定性打磨

问题 24 — 默认列表反复出现
问题：默认列表反复出现。用户清除所有追番数据后刷新页面，之前删掉的 20 个默认番剧又回来了。原因是 loadAnimeList() 在 localStorage 为空时总是返回默认列表，无法区分"第一次访问"和"用户主动清空"。
解决：添加了 tushanmumu_anime_user_initialized 标记。第一次访问（标记不存在）→ 显示默认列表；用户添加/清空过数据后，saveAnimeList 会设置标记为 '1'；之后如果 localStorage 为空但标记存在，说明是用户主动清空的，返回空数组而不是默认列表。这样既保留了首次访问的默认展示，又尊重用户的清空操作。
问题 25 — 移除错误的默认列表
问题：默认列表的 media ID 全是错的。之前为了演示效果随便填了 20 个 md 编号，但点击"JOJO的奇妙冒险 石之海"跳转到的根本不是 JOJO 的页面。用户发现后把默认列表全删了，结果刷新后又回来了。
解决：直接移除了默认列表，改成空列表启动。用户自己添加的番剧才是准确的，不需要预置一堆错误数据。云数据库 anime_database.json 保留着，用户添加番剧时自动匹配封面和评分。
问题 26 — 浏览器端方案全部失败
问题：云数据库只有 20 条预存数据，用户添加新番剧时封面和评分获取失败。尝试重新实现 JSONP 方案（<script> 标签绕过 CORS），但 B 站对浏览器端所有请求方式都做了封锁——JSONP 返回 script load error，直接 fetch 被 CORS 拦截。至此确认：B 站 API 从浏览器端完全无法访问，没有任何绕过手段。
解决：已回退到问题 25 修复后的稳定版本。当前状态：空列表启动，云数据库可匹配预存番剧的封面和评分，新番剧需手动填写名称和封面 URL。后续考虑的方案：让用户在 B站番剧页面右键复制封面链接粘贴进来，或者用浏览器扩展/本地脚本预处理数据。
问题 27 — 第一次点击没反应
问题：每次点击"添加"按钮，第一次总是没反应，第二次才能成功添加。原因是确认添加的处理函数是 async 异步的，里面有一段等待 enrichRunning 标志位的 await 循环。虽然默认列表为空时这个循环理论上会直接跳过，但异步函数的执行上下文切换导致第一次点击被"吞掉"了。
解决：移除了不必要的 enrichRunning 等待循环（默认列表已清空，不需要等），给处理函数加了 confirmAddProcessing 防重复点击标志和 try/catch 错误捕获。现在第一次点击就能正常添加。
问题 28 — 防盗链与封面获取
问题：封面图片即使 URL 正确也加载不出来。B站的图片服务器（hdslb.com）有防盗链机制，会检查请求的 Referer 头，发现不是从 B站 页面发出的请求就拒绝返回图片。GitHub Pages 域名的请求全被拦截。
解决：在封面 <img> 标签上加了 referrerpolicy="no-referrer"，让浏览器加载图片时不带 Referer 头，绕过防盗链检查。注意不能在全局 <head> 加 <meta name="referrer">，否则 JSONP 的 <script> 请求也不带 Referer，B站 API 会拒绝。同时增加了多种封面获取方式：① 输入 md 编号后 API 自动填充封面 URL（JSONP 方式获取）；② 弹窗里新增"打开B站番剧页面"按钮，一键跳转到 B站对应页面，右键封面图 → 复制图像链接 → 粘贴到封面输入框。不填封面则显示粉色渐变背景。
问题 29 — dataset.editIndex 为 undefined
问题：第一次点击"添加"按钮总是失败，弹窗关闭但番剧没有被添加到列表，第二次点击同样的信息才能成功。根因是 confirmAdd 按钮的 data-edit-index 属性在页面加载时不存在，dataset.editIndex 返回 undefined。代码中检查 if (editIndex !== '') 时，undefined !== '' 为 true，误进入了编辑模式分支。编辑模式中 parseInt(undefined) 得到 NaN，animeList[NaN] 为 undefined，所以什么都没做。第二次点击时，因为第一次执行后 clearModalFields 设置了 dataset.editIndex = ''，检查通过进入添加模式，所以成功了。
解决：在页面加载时初始化 document.getElementById('confirmAdd').dataset.editIndex = ''，确保第一次打开弹窗时 editIndex 是空字符串而不是 undefined。同时修改检查条件为 if (editIndex !== '' && editIndex !== undefined) 双重保险。添加了详细的 console.log 调试日志，方便后续排查问题。

问题 30 — JSONP 重试与备用端点
问题：JSONP 自动填充番剧信息不稳定——清除浏览器缓存后第一次输入 md 编号经常获取失败（控制台报 JSONP load error 或 JSONP timeout），但等一会儿再试又成功了。根因是 JSONP 通过 <script> 标签发起真实网络请求，清缓存后 DNS 解析、TCP 建连、TLS 握手都要重新来，叠加 B站 API 的频率限制，第一次请求容易超时（原超时仅 8 秒）。
解决：三管齐下提升可靠性。① 超时时间从 8 秒提升到 15 秒，给慢网络更多余量。② 加入自动重试机制（指数退避）：第一次失败后等 2 秒重试，再失败等 4 秒第三次尝试，最多重试 2 次。③ 增加备用 API 端点（pgc/view/web/season），主端点全部重试失败后自动切换尝试。三层保障大幅提升了自动填充的成功率。
问题 31 — file:// 协议限制
问题：本地 file:// 协议下测试 JSONP 自动填充仍然不稳定，即使加了重试机制，清缓存后首次请求也经常失败（控制台报 net::ERR_FAILED）。根因是浏览器将 file:// URL 视为"独立安全源"（unique security origin），对跨域网络请求施加了更严格的限制，导致 <script> 标签加载 B站 API 时直接被浏览器拒绝，连超时都等不到。
解决：将网站部署到 GitHub Pages（https://tushan-mumu.github.io），用正式的 HTTPS 域名替代 file:// 协议。部署后测试确认：JSONP 自动填充在清缓存后也能稳定成功，番剧名称、评分、封面均可自动获取。file:// 本地测试和线上 HTTPS 环境的浏览器安全策略差异，是导致同一份代码表现不同的根本原因。至此，追番系统的自动填充功能在线上环境已完全可用。
问题 32 — 批量添加性能优化
问题：批量添加番剧时速度很慢。原因是批量添加采用串行方式逐个请求 B站 API 获取元数据（名称、封面、评分），每部番剧要等上一个请求完成（含重试最长约 45 秒）才开始下一个，添加 10 部番剧可能需要好几分钟。
解决：三处优化。 新增会话级元数据缓存（metaCache），同一 mediaId 首次获取后存入内存，后续请求直接命中缓存，避免重复调用 API。② 引入并发请求机制（fetchConcurrent），最多同时发 3 个请求，将批量添加从串行改为并行，速度提升约 3 倍。③ 批量添加弹窗新增进度条和实时文字提示（"已获取 5/12（成功 4）"），用户能清楚看到进度，不再觉得卡住。
问题 33 — 跨设备数据同步
问题：追番数据存在浏览器 localStorage 中，每台电脑、每个浏览器的数据完全独立。用户在 A 电脑添加的番剧，在 B 电脑上完全看不到，无法跨设备同步。
解决：新增"导出"和"导入"功能。导出：将当前追番列表序列化为 JSON 文件下载到本地（文件名含日期，如 tushanmumu_anime_2026-08-06.json）。导入：选择之前导出的 JSON 文件，自动解析并与现有列表合并（按 biliUrl 去重，跳过重复项）。用户在 A 电脑导出文件，传到 B 电脑后导入，即可完成数据迁移。按钮放在追番页面顶部操作栏，与批量删除、批量添加并列。
